Round 3 — Power Mode: Password Reset (email via Resend)

Mode: Power.

Context from Round 0: auth uses opaque session tokens + bcrypt passwords. change-password exists (requires the current password), but there is no password reset — a user who forgets their password is locked out permanently. This round adds an email-based reset using Resend, with a 6-digit code entered in-app (no deep-link / universal-link infra needed).

Behavior

Backend

Schema — add storage for reset codes (a password_reset_tokens table or equivalent), following the existing text("user_id") convention used elsewhere — do not introduce a real FK to users.id (the schema's user_id columns are text while users.id is serial; stay consistent). Store the hash of the code (never plaintext), the user reference, an expiry timestamp, and a used/consumed marker.

POST /auth/forgot-password { email }


Always return 200 with a neutral response, whether or not the email matches an account (anti-enumeration — never reveal whether an address is registered).
If a matching user exists: generate a 6-digit numeric code, store its hash with a short expiry (15 minutes), invalidate any prior unused codes for that user, and send the code to the user's email via Resend.
Rate-limit by email and IP so the endpoint can't be used to spam or enumerate.


POST /auth/reset-password { email, code, newPassword }


Verify the code against the stored hash and that it's unexpired and unused; reject expired, already-used, or incorrect codes with a clear error.
Validate the new password (enforce a minimum length consistent with registration).
Hash the new password with the existing bcrypt path (cost 12) and update it.
Mark the reset code consumed (single-use).
Invalidate existing sessions for that user (null the session token / expiry) so any active session is logged out after a reset.
Return success.


Resend integration


API key from env (RESEND_API_KEY). Use a verified sending domain; until one is configured, fall back to Resend's test sender (reaches only the account owner's email) so the flow is verifiable.
A simple transactional email: the 6-digit code and a line noting it expires in 15 minutes. Plain and clear — no marketing chrome.


Frontend (login / auth screens)


"Forgot password?" entry on the login screen.
Step 1 — enter email → call forgot-password → always advance to the code screen with a neutral message ("If an account exists for that email, we've sent a code").
Step 2 — enter the 6-digit code + new password (+ confirm) → call reset-password → on success, route to login (or sign in) with a confirmation; on failure, show a clear error (bad/expired code, weak password).
Include a "resend code" affordance and basic client-side validation (code length, password match/length).


Acceptance criteria


forgot-password returns 200 identically for registered and unregistered emails (no enumeration signal in status, body, or timing where avoidable).
A valid, unexpired code lets the user set a new password and log in with it.
Codes are single-use and expire — reused or expired codes are rejected.
After a successful reset, any previously active session token is rejected on the next request.
Repeated rapid forgot-password calls are rate-limited.
Reset codes are stored hashed, never in plaintext.
A real reset email is delivered via Resend (verify end-to-end to your own account email).


Out of scope


Deep-link / universal-link reset (using an in-app code instead).
Session sliding-expiry / rotation (Round 4).


Checkpoints


Schema + both endpoints + Resend send, verified against a real email (request code → reset → log in with new password), including the session-invalidation and anti-enumeration behavior.
Front-end forgot/reset flow wired and verified on an EAS dev build.


Done when a user who can't log in can request a code by email, enter it in-app with a new password, and sign in — with codes hashed, single-use, expiring, rate-limited, and old sessions invalidated on reset.
